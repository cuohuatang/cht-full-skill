# 20 · 极简代码（lean-code）：Ponytail 的范围纪律

> 来源：[DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail)（**DietrichGebert，MIT**，约 19.4 万★，Ponytail 5）。六个纯文本 skill（`skills/ponytail*/SKILL.md`）+ `LICENSE` 已**原样嫁入**（sha256 与上游一致）；JS hooks 运行时、各宿主 plugin 目录、benchmarks、`.toml` 命令**不嫁**（与 cht「0 依赖」冲突， hooks 属宿主专属运行时）。本文件为中文重述与 cht 集成边界，原文以嫁入的 SKILL.md 为准。

## 一句话定位

**让 AI 像房间里最懒的高级工程师那样思考：最好的代码是你没写的那行。** Ponytail 治的是 AI 写代码最常见的病——**过度设计**：没人要的抽象层、没人设的配置项、几行功能引一个依赖、为"以后"预留的扩展点。

## 与既有机制的分工（先读这段，避免打架）

| 机制 | 管什么 | 不管什么 |
|---|---|---|
| `/cht-lean`（本文件） | **范围纪律**：写之前爬阶梯定"最小完整改动"，写完查肥肉（review/audit/debt） | 不管过程顺序、验证深度 |
| `/cht-ub` | **过程纪律**：三段式（Work→Right→Practice）+ 量化门（CRAP/重复度/变异） | 不管"该不该写这么多" |
| `/cht-spec` | 需求逼问：把"想做什么"问清楚 | 不管实现多省 |
| 三条铁律 | 验证证据：没跑过不许说完成 | 永远优先于任何"懒" |

两者互补：ub-mode 决定**怎么把代码做对**，Ponytail 决定**一开始就不写多余的部分**。典型组合：`/cht-lean` 先砍范围 → 三段式逐步交付 → 量化门收尾。

## 核心一：6 步决策阶梯（动手前，从上往下取第一个能完整解决的）

> ⚠️ 注意：上游 `AGENTS.md`/`SKILL.md` 实际是 **6 步**（早期二手资料与旧方案文档写"7 步"，以嫁入原文为准）。

```
1. 真需要存在吗？        没人要的功能/选项/灵活性一律砍，且用一行点名砍了什么。
                         模糊需求（"给我做个X"）→ 只做核心功能的最小版。
2. 代码库里已有？        有现成的 helper/组件/服务/模式 → 按周边代码的用法用它。
3. 标准库/平台能力？     能做就用——除非项目有自己的封装（自家组件 > 原生控件）。
4. 已装依赖能做？        能就用。绝不为几行代码新增一个依赖。
5. 一行能搞定？          读者一眼能懂的一行，就写一行。
6. 都不行                → 写能工作的最少代码。
```

配套约束（同一原文，逐条）：

- **对方案懒，对事情不懒**：任务要求的每一部分（被你改动的调用方、测试、fixture）都要收尾。
- **不加没人要的东西**：抽象、包装层、类型转换、选项、配置、样板、"为以后"的代码一律不写；值保持平台本来的形态；**删除优于新增**；沿用代码库既有的层次、接口与惯例。
- **最短可工作 diff 获胜**——前提是你已列全改动必须触及的所有位置；需要解码才能看懂的"一行"不算短。
- 注释只写代码表现不出的 **why**，一行。
- **修 bug：先 grep 该函数的所有调用方**，然后在共享代码里一次修根因，别在每个调用方各贴一块创可贴。
- 移动/合并的代码保留原有的错误处理与校验。
- 同等大小的方案里，选**边界情况处理正确**的那个。
- **懒代码没带自检就不算完成**：新写非平凡逻辑（分支/循环/解析器/**金额或安全**/整段脚本）留一个小测试或 assert 自检；琐碎改动不需要。
- 带已知上限的捷径，写成这种注释：`shortcut: <上限>, <何时升级>`。

**绝不砍（Never cut）**：信任边界处的校验、防数据丢失的错误处理、安全、可访问性、真实硬件所需的校准、用户明确要求的任何东西。

## 核心二：三档强度

| 档 | 行为 |
|---|---|
| **lite** | 只做被要求的。用一行点名更小的选项，让用户挑。 |
| **full**（默认） | 上述全部规则 + 结尾 1–2 行说明"跳过了什么、没查什么、有什么风险"。 |
| **ultra** | 额外**质询请求本身**：动手前对需求不支撑的部分直接推回。 |
| **off** | 退出（说"stop ponytail" / "normal mode" 亦可）。 |

档位持续整个会话。cht 集成默认 **full**；ultra 与 `grill-me` 的"防擅自做主"同向，可叠加。

## 核心三：五个配套 skill 的分工

| skill | 一句话 | 时机 |
|---|---|---|
| `ponytail` | 懒人模式本体：最小改动 + 结尾交代跳过项与风险 | 写代码前激活 |
| `ponytail-review` | **diff 级**评审：对→安全→承压→有测→够快→精简，每条发现四要素（是什么/问题/最小修法/不修的后果），编号可"修 2 和 5" | 改完一处之后 |
| `ponytail-audit` | **全仓级**评审：同上六维 + 建图先行、按代价排序，最多 20 条，结尾给 Verdict 与 `Lean: -N 行, -M 依赖` | 接手存量仓库 |
| `ponytail-debt` | 收割全仓 `shortcut:` 注释成台账；**无升级触发器的标 `no-trigger`——那才是会烂掉的** | 定期巡检 |
| `ponytail-gain` | 展示官方基准记分牌（39 任务×5 次，LOC −53% / token −45% / 成本 −26% / 时间 −41%，隐藏正确性检查 97%） | 了解收益 |

评审两条铁规（review/audit 共用）：**每条发现必须给出具体案例**（"这个输入导致这个错误结果"），无案例不成立；`shortcut:` 注释里写明上限的是**决策不是发现**，除非预期负载已越过它。

## 诚实边界（上游自带，必须遵守）

`ponytail-gain` 明文：这些是**基准均值，不是你这个仓库的数字**。**永不编造"本仓库节省了 X 行/X token"**——没写出来的那个版本从未存在，没有真实基线可减。本仓库唯一真实的数字来自 `/ponytail-debt` 的计数台账。

## cht 集成边界与冲突裁决

1. **懒 ≠ 少验证**：Ponytail 的"一个非平凡逻辑留一个小测试"是**下限**；cht 铁律（RED before GREEN、本轮新跑的验证证据）照旧全量执行。冲突时 **cht 三条铁律 > ponytail 懒规则**。
2. **懒 ≠ 跳过 spec/plan**：阶梯是 **Build 阶段的范围决策工具**，不替代阶段 0 六问与计划；恰恰相反——先爬阶梯，spec 会更短。
3. **与 theater-detection-audit 的互补**：`/cht-doctor` 扫"假实现"（壳），`/cht-lean audit` 扫"真实现但多余"（肥肉）。方向相反，都值得跑。
4. **最小改动也有验收**：结尾必须保留 full 档的"跳过了什么/没查什么/风险"交代——这与三条铁律第 3 条同源。
5. **金额与安全逻辑不受"懒"豁免**：原文自己就把 money/security 列为必须留测试的非平凡逻辑；cht 再加一层：报价/金额/鉴权改动走 `/cht-doctor` 四层验证门。

## 红牌（违反即停）

- 以"ponytail"为借口砍掉用户明确要求的功能或校验。
- 新增依赖、新抽象层、新配置项却没有爬过阶梯的证据（1–5 步为何都不行）。
- 编造"本仓库节省 X"的数字。
- 用 lite/ultra 档位静默改写用户需求而不是推回确认。
- 评审发现不给具体案例、只给"建议考虑"式模糊担忧。
- 拿基准记分牌冒充本仓库实测。
