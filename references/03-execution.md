# 03 · 实现执行（Build）

> 计划已经把思考做完了。这个阶段只做三件事：**照计划做、用测试证明每一步、留下能被遗忘的自己读懂的记录。**

---

## 1. TDD 循环（不可协商）

```
RED   写一个失败的测试 → 跑 → 必须看到它失败，且失败原因正确
GREEN 写最小实现让它过 → 跑 → 通过
REFACTOR 清理重复与命名 → 跑 → 仍然通过
COMMIT 一次提交，信息写清做了什么、为什么
```

**核心判据：没看见它失败，你就不知道它测的是不是那件事。**

### RED 阶段的强制检查

看到测试失败后，读失败输出，回答：

- 失败在**断言**上，还是失败在语法错误 / import 错 / 测试没被收集？后三种不算 RED。
- 失败的**信息**说的是预期的事吗？（"expected 2 items, got 0" 是；"TypeError: extract is not a function" 不是）
- 如果测试一次就过了：把实现注释掉，确认它变红，再恢复。否则你写的是**恒真测试**。

### 例外（必须问用户）

- 一次性原型、一次性脚本
- 生成的代码（codegen 产物）
- 纯配置文件、资源文件
- 探索性 spike（明确声明是 spike，事后丢弃或补测）

心里冒出"这次就先不写测试了"——停。那是合理化。

### 测试写什么

| 该测 | 不该测 |
|---|---|
| 外部可观察的行为 | 私有方法、实现细节 |
| 边界：空、1、多、超限、非法 | 框架本身的功能 |
| 错误路径与其类型 | 日志文本 |
| 回归：每个修过的 bug 一条 | 为了覆盖率的空断言 |

断言必须有实质。`expect(result).toBeDefined()` 这种几乎不算测试。

## 2. 两种执行模式

| | **子代理驱动**（默认，任务相互独立时） | **内联执行**（任务强耦合 / 无子代理能力 / 用户要求省钱） |
|---|---|---|
| 做法 | 每个任务派一个新代理实现，任务后派评审 | 你自己顺序做完全部任务 |
| 成本 | 每任务两份新上下文 | 一份上下文 + 末尾一次评审 |
| 收益 | 每个任务都有新鲜视角 + 双人复核 | 上下文连续，交接无损 |
| 代价 | 贵、慢、需精心写简报 | 没有逐任务复核 |

选择规则：

- 任务之间有共享状态或强顺序依赖 → 内联
- 任务独立、可并行、每个都能独立验证 → 子代理
- 用户明确说"省点"或任务 < 3 个 → 内联

---

## 3. 子代理驱动：怎么写简报

子代理**不继承**你的会话历史。你构造什么，它就知道什么。

简报模板见 `assets/templates/ROLE-BRIEF.md`。必须包含：

1. **背景 3 句**：这是什么项目，这个任务在整条链路的哪一环。
2. **精确任务**：文件路径、接口签名、行为规格（含错误行为）。
3. **相关代码**：把要改的文件和它依赖的接口贴进去（不要让子代理自己去翻整个仓库）。
4. **验证命令**：它能自己跑的那条。
5. **边界**：不许改哪些文件，不许引入哪些依赖。
6. **完成标准**：可判定的列表。

不要写"参考一下我们的代码风格"——它没有你的上下文。要写"用 `Result<T, E>` 而非抛异常，见 `src/core/result.ts`"。

## 4. Ledger（执行账本）

跨任务、跨上下文唯一的记忆载体。写在 `docs/cht/LEDGER.md`，每完成一步追加一行：

```
[T3] 2026-10-29 14:02 RED   extract.spec.ts::空文本 → 断言失败（预期）
[T3] 2026-10-29 14:05 GREEN 实现 8 行，通过，commit a1b2c3d
[T4] 2026-10-29 14:20 RULING 选择同步调用而非队列 —— 量级不需要异步，出错代价是延迟+200ms
[T4] 2026-10-29 14:31 BLOCKED 飞书 webhook 签名校验失败，怀疑 body 规范化问题
```

规则：

- 每条一行，不写叙事。
- RED 与 GREEN 都要记，这是"我看过它失败"的唯一证据。
- 裁决（Ruling）必须记，格式：`决定 — 为什么 — 错了的代价`。
- 阻塞（Blocked）记下当时的假设，方便回来接。

**连续执行**：不要在任务之间停下来问"要继续吗"。用户选的是执行，不是陪着点确认。只有第 5 节的四种情况停。

## 5. 裁决而不是停摆

计划在跑的时候不等人类。冲突、歧义、计划缺陷、你本来想申请的超限——**自己定**。

```
SPEC 是最终权威，PLAN 是对它的论证，你的判断解决两者都没回答的部分。
```

判定优先级：SPEC > PLAN > 项目既有惯例 > 你的判断。

只有四件事真的能停：

1. 不可逆或破坏性操作（删数据、`rm -rf`、强推、清库、覆盖远程）
2. 安全敏感（密钥、权限提升、对外暴露、生产写操作）
3. 工作区之外的副作用（合并到共享分支、发布、发消息、花钱）
4. 计划已崩到每条路都是猜的

其余继续做，把裁决写进 ledger。

---

## 6. 提交纪律

- 一次任务一次提交，提交信息：`type(scope): 做了什么`
- 提交前跑该任务相关的全部测试（不是只跑新写的那条）
- 不把无关改动混进同一个提交（顺手格式化整个文件是大忌）
- 不提交：密钥、`.env`、调试 `console.log`、注释掉的旧代码、`TODO` 占位实现
- 不 `--amend` 已推送的提交，不 `--no-verify` 跳过钩子（钩子挂了就修钩子或修代码）

---

## 7. 中途发现计划错了怎么办

计划错了是常态，处理方式分三种：

| 情况 | 动作 |
|---|---|
| 局部细节错（命名、参数顺序） | 直接改，记 ledger |
| 任务拆分错（一个任务太大 / 顺序反了） | 改 `PLAN.md` 的对应任务，记 ledger，继续 |
| 根本假设错（接口设计不可行、依赖用不了） | **停**，回到阶段 2 重做该部分计划，告诉用户"计划的前提变了" |

第三种要停，因为它会让后续所有任务一起错。
