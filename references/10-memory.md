# 10 · 记忆、复盘与跨会话连续性（Reflect）

> 上下文会被截断，会话会结束，人会忘。所以判断必须**落到文件里**，否则它就会在明天早上消失，
> 而你会重新犯同一个错——还以为自己在思考。

---

## 1. 三层记忆

| 层 | 位置 | 存什么 | 生命周期 |
|---|---|---|---|
| **账本 Ledger** | `docs/cht/LEDGER.md` | 本次任务的每一步：RED/GREEN、裁决、阻塞 | 一个任务周期 |
| **学习 Learnings** | `docs/cht/LEARNINGS.md` | 跨任务可复用的判断：这个代码库的坑、用户的偏好、环境怪癖 | 长期，随项目走 |
| **复盘 Retro** | `docs/cht/RETRO.md` | 每个里程碑的回顾：做对什么、做错什么、下次改什么 | 每 1–2 周或每个版本 |

判断写在哪一层：

- 只跟这次任务有关 → Ledger
- 下次还会用到 → Learnings
- 关于「我们怎么工作」的元判断 → Retro

---

## 2. Learnings 的写法

**格式**：一句可执行的判断，不是故事。

```
✅ 好：这个项目的 `pnpm test` 默认并行跑，涉及数据库的测试必须在 `vitest.config.ts` 里串行化，
      否则会因共享 fixture 偶发失败。
✅ 好：用户明确要求所有对外接口返回 camelCase，即便数据库是 snake_case。
❌ 差：今天调试了很久数据库测试的问题。（这是叙事，不是知识）
❌ 差：注意测试的稳定性。（不可执行）
```

分类建议（用标签，方便检索）：

```
[环境] [约定] [坑] [偏好] [依赖] [流程]
```

示例：

```
[坑] 飞书 webhook 签名校验要求 body 是原始字节，JSON.stringify 后再签名会失败。
     正确做法：先拿 raw body 签名，再 parse。
[约定] 新增 API 端点必须在 `src/routes/index.ts` 注册，否则 404 且无日志。
[偏好] 用户不喜欢一次给超过 5 个方案，超过就自己筛到 3 个。
```

维护规则：

- 每条后面标日期与来源（哪个任务学到的）
- 每季度或每 20 条清理一次：过时的删掉，重复的合并
- **超过 30 条的 Learnings 文件等于没有 Learnings**（没人读）

## 3. Ledger 的写法

见 `references/03-execution.md §4`。核心：一行一条，含时间、类型、内容。

类型固定四种：`RED` `GREEN` `RULING` `BLOCKED` `DEBUG`。

会话被压缩或换人接手时，**先读 Ledger**，不要重新摸索。

## 4. 复盘（Retro）

时机：每个版本发布后、每个大任务结束后、每次连续两次翻车之后。

模板：`assets/templates/RETRO.md`。四个问题，不要写长：

```
1. 哪些做对了？（具体到动作，不写"沟通顺畅"）
2. 哪些做错了？（具体到决策，不写"时间不够"）
3. 哪个假设错了？（这是最有价值的一栏）
4. 下次具体改什么？（一条可执行的动作，不是"加强重视"）
```

评判标准：**如果这四条别人看了不能照着做，复盘就是失败的。**

反例：「这次需求理解不够充分，下次要加强沟通。」——零信息。
正例：「这次把'支持多语言'当成了默认需求，实际用户只有中文场景。下次在 SPEC 的非目标栏里，把没被明确要求的能力全部写进非目标。」

## 5. 指标（用来判断流程是否在工作）

| 指标 | 怎么看 | 健康值 |
|---|---|---|
| 一次通过率 | 首次 PR 就过评审的比例 | > 60% |
| 回归率 | 修好的 bug 又回来了的比例 | < 5% |
| 门禁降级次数 | 每周弱化测试/放宽超时的次数 | 趋近 0 |
| 任务粒度 | 平均每个提交改多少行 | 50–200 |
| 计划偏差 | 实际任务数 vs 计划任务数 | < 30% 偏差 |

指标只用来发现问题，不用来考核人。**拿指标考核，指标就失效。**

## 6. 跨会话连续性

新会话开始时，按此顺序读（有则读，无则跳过）：

```
1. docs/cht/LEDGER.md     最近 20 行 —— 上次做到哪
2. docs/cht/SPEC.md       范围与非目标 —— 别越界
3. docs/cht/PLAN.md       剩余任务
4. docs/cht/LEARNINGS.md  这个项目的坑与约定
5. 最近 5 条 git log
```

读完在回复里用 3 行说清：「上次做到 X，当前状态 Y，下一步 Z」。**不要假装记得细节**——读到的才算知道。
