# /cht-spec — 需求梳理与规格定稿

## 参数

| 参数 | 作用 |
|---|---|
| （无） | 需求已较清晰，直接落规格，边落边确认 |
| `--discover` | 先跑六问诊断，戳破伪需求 |
| `--quick` | 只做 3 个关键问题 + 一页规格（小改动） |

## 执行

1. **判断信息完整度**：两个合格工程师会不会写出不同的东西？不会 → 直接做，报告改了什么，到此结束。
2. **（`--discover`）六问**，一次只问一个，按阶段选问（`references/01-discovery.md §2`）：
   - Q1 需求真实性 · Q2 现状替代 · Q3 具体的绝望 · Q4 最窄楔子 · Q5 观察与意外 · Q6 未来契合
   - 每问追问到出现**具体的人、具体的数字、具体的行为**为止
   - 用户两次拒绝回答 → 停止追问，用已有信息继续
3. **挑战前提**：至少指出一个用户没意识到的假设（格式见 `references/01-discovery.md §3`）。
4. **给 2–3 个方案**，带工作量/风险/代价，推荐项必须由用户自己的证据支撑。**停下来让用户选。**
5. **分块写 SPEC**：每块 3–8 行，确认后再给下一块。四块必须齐：
   范围 / 非目标 / 可判定的验收标准 / 成功度量。
6. 落盘 `docs/cht/SPEC.md`（模板 `assets/templates/SPEC.md`）。

## 禁止

- 需求没确认就列技术方案
- 一次倒出 2000 字让用户"看一下"
- 把"支持多语言""要有权限系统"未经验证就写进范围（应进非目标）

## 完成判据

- [ ] 六问该问的都问了（或用户明确拒绝）
- [ ] 至少一个隐藏假设被摆到桌面
- [ ] 用户选定了一个方案
- [ ] SPEC 四块齐全，验收标准条条可判定
- [ ] 用户明确说过"可以"
