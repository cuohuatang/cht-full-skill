# 04 · 系统化调试（Debug）

> **铁律：没有完成根因调查，不许提出修复。**

症状修复是失败。看到报错就改一行然后祈祷，是最昂贵的工作方式——它把一次 20 分钟的调查换成三次 2 小时的返工。

---

## 适用场景（一切技术问题）

测试失败、线上 bug、行为异常、性能退化、构建失败、集成失败、偶发问题、环境差异。

没有例外。"这个很明显，就是 null 判断漏了"——那也要先证明它确实是 null，且是**这一处**的 null。

---

## 四阶段

### 阶段 1 · 复现与定位（没做完不许改代码）

1. **稳定复现**：给一条命令 / 一串操作，每次都能看到同样的失败。不能稳定复现就先解决"为什么不能稳定复现"。
2. **缩小范围**：二分。注释一半、换输入、换环境、`git bisect`。目标是把"整个系统坏了"变成"这个函数对这类输入返回错"。
3. **读错误全文**：不是第一行。栈顶、`caused by`、退出码、日志上下文 20 行。
4. **对照近期变更**：`git log --oneline -20`，`git diff` 上次绿灯以来的改动。新引入的东西嫌疑最大。
5. **确认假设**：把你认为的原因写成一句可证伪的话——"如果原因是 X，那么 Y 应该成立"。然后去验证 Y。

阶段 1 的产出必须是一句话：

```
根因假设：<哪里> 在 <什么条件> 下 <做了什么错事>，因为 <机制>。
证据：<我跑过的命令与它的输出>。
```

写不出这句话，说明还在阶段 1。

### 阶段 2 · 假设检验

- 一次只验证一个假设。同时改三个变量，等于什么都没验证。
- 优先用**最便宜的实验**：加日志、写一个 5 行的复现脚本、在 REPL 里跑。
- 实验要有预期结果。"我加个 log 看看"不是实验；"如果假设成立，这个 log 应该打印 3 次"是。
- 假设被推翻是好事——记下来，排除一个方向。

### 阶段 3 · 修复

- 修**根因**，不是症状。给 `try/catch` 吞掉异常、加 `?? fallback` 掩盖 undefined、提高超时时间——这些都是症状修复。
- 先写一条会失败的回归测试（复现那个 bug 的最小测试），再修。修完它必须变绿。这是 TDD 用在调试上。
- 修完跑全量测试，确认没连带打坏别的。
- 检查同类问题：这个 bug 的模式在别处存在吗？（同一个 API 的其他调用点、同一个模式的其他模块）

### 阶段 4 · 复验与记录

- 用阶段 1 的原始复现步骤再跑一遍，确认不再复现。
- 贴出证据（命令 + 输出）。
- 记 ledger：`[DEBUG] 根因 … / 修复 … / 回归测试 … / 同类位置检查 …`

---

## 三次失败就停

同一问题连续 3 次修复尝试失败，**立刻停止改代码**，改为：

1. 列出已排除的假设（这是资产，不是浪费）
2. 列出当前最强的假设，以及它缺什么证据
3. 换视角：派一个全新上下文的代理重新看（它没有你的错误锚定）
4. 找用户要信息：环境、日志、可复现步骤、最近改了什么
5. 考虑降级方案：能不能绕过这块？（不改根因，但先止血，并明确标注为技术债）

继续第四次盲改的代价远高于停下来沟通。

## 常见错误模式（先对照这些）

| 现象 | 常见根因类别 | 先查什么 |
|---|---|---|
| 本地好、CI 挂 | 环境差异 | Node/Python 版本、时区、locale、文件系统大小写、并行度 |
| 偶发失败 | 竞态 / 顺序依赖 / 共享状态 | 异步等待、测试间共享变量、时间相关断言 |
| 改了 A 坏了 B | 隐式耦合 | 全局状态、单例、共享可变对象 |
| 只在生产挂 | 数据规模 / 配置 / 网络 | 数据量级、超时、连接池、代理、DNS |
| 类型都对但结果错 | 语义错误 | 单位、时区、精度、编码、off-by-one |
| 内存/CPU 慢慢涨 | 泄漏 | 事件监听未解绑、缓存无上限、闭包持引用 |

---

## 反模式清单

| 反模式 | 为什么错 |
|---|---|
| "先试试这个" 式改代码 | 没有假设的实验，只是随机搜索 |
| 一次改多处 | 成功了不知道哪处起作用，失败了不知道哪处有害 |
| 用 `try/except` 吞掉 | 把可观测的失败变成不可观测的失败 |
| 提高超时 / 增加重试来"修复" | 掩盖了真正的性能或一致性问题 |
| 删掉失败的测试 | 删的是证据 |
| 相信"我本地是好的" | 本地好是信息，不是结论 |
| 不看完整错误输出 | 90% 的答案在堆栈下半部分或 `caused by` |
