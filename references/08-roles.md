# 08 · 八角色作战手册（Roles）

> 同一个需求，用八个视角各看一遍。每个角色只问一个问题，但那个问题有**否决权**。
> 你不必真的派八个代理——你可以一个人快速切换视角，每个 2 分钟。但**不能跳过**。

---

## 角色速查

| 角色 | 唯一问题 | 产出 | 否决权 |
|---|---|---|---|
| CEO / 创始人 | 这值得做吗？有没有更小的切口？ | 范围决定 | 砍需求 |
| 产品经理 | 验收标准可测吗？ | SPEC | 打回不可测的验收 |
| 架构师 | 数据怎么流？失败长什么样？ | 数据流图 + 错误矩阵 | 打回隐藏假设 |
| 设计师 | 这是产品还是模板？ | 设计维度评分 | 打回低分设计 |
| 工程师 | 每个任务能被一个测试证明吗？ | 代码 + 测试 | — |
| 评审工程师 | 哪个 bug 能过 CI 但炸线上？ | REVIEW | 阻断合并 |
| QA | 真实环境跑通了吗？有证据吗？ | QA-REPORT | 无证据不算过 |
| 发布工程师 | 出事怎么退？ | PR + 回滚方案 | 无回滚不许发 |

外加两个横向视角：**安全官**（并入评审工程师）、**数据分析**（并入 CEO 与 QA）。

---

## CEO / 创始人

**只问**：如果只有一个功能能留，留哪个？

做法：
1. 把需求重述成一句"用户会得到的改变"，不是功能列表。
2. 找 10 分产品：用户说了 A，他真正要的是不是 A+B+C 合成的那个东西？（说了"日报工具"，实际要"幕僚长"）
3. 四档定范围：扩张 / 选择性扩张 / 维持 / 收缩。
4. 写出一句**用户上线后会说的人话**："以前要花 40 分钟整理，现在打开就有。"

反模式：把用户提的所有功能都当需求；用"以后可能要"给自己加活。

---

## 产品经理

**只问**：这条验收标准，我能用一条命令判定吗？

做法：
1. 每条验收标准配一个判定动作（命令、点击序列、API 调用）。
2. 写非目标清单，写得比范围还细。
3. 定义成功度量：上线后看哪个数、基线多少、目标多少。
4. 分块给用户确认（每块 3–8 行）。

反模式：写"体验流畅""性能良好"；需求里混实现方案；一次糊 2000 字让用户"看一下"。

---

## 架构师 / 工程经理

**只问**：这里哪个假设没被验证？

必产出四件：

1. **数据流图**（ASCII 够用）：

```
请求 → [校验] → [业务] → [持久化] → 响应
         ↓失败      ↓失败       ↓失败
       400        retry×2     500 + 告警
```

2. **状态表**：状态 × 触发 → 新状态。含非法转移的处理。
3. **错误矩阵**：每个外部依赖 × 每种失败模式 → 系统行为。
4. **测试矩阵**：任务 × 测试文件 × 断言点。

再加两项检查：
- **边界**：空/1/多/超限/并发/重复/时区/编码
- **迁移**：有 schema 变更吗？能 down 吗？

反模式：只画 happy path；把"应该没问题"当结论；接口先写实现再想签名。

---

## 设计师

**只问**：这个界面，换个产品名能不能直接用？

七个维度各打 0–10，并说明 10 分长什么样（见 `references/02-planning.md §4.2`）：视觉层级、布局密度、文案、三态（空/加载/错）、交互反馈、一致性、AI 味。

**AI 味红线**（命中任一即扣到 6 分以下）：

- 紫→蓝渐变、发光边框、玻璃拟态堆叠
- 居中大标题 + 副标题 + 两个按钮的首屏模板
- 三列等宽功能卡片 + 线性图标
- emoji 当图标
- 所有卡片都是白底 + 大圆角 + 淡阴影
- 没有真实内容的占位文案（Lorem ipsum、"功能一"）

改法：从**内容**出发定版式。先写好真实文案，再决定用什么布局装它。宁可朴素但准确，不要华丽但通用。

反模式：先挑配色再想内容；每个区块都加卡片；用动画掩盖信息结构不清。

---

## 工程师

**只问**：这个任务，我能先写出一条会失败的测试吗？

做法见 `references/03-execution.md`。要点：

- 一个任务一次提交，提交前跑该任务全部测试
- 不写"以后会用到"的抽象（YAGNI）
- 重复三次以上才抽象（DRY 的前提是第三次）
- 命名即文档：`extractActionItems` 好过 `process`

反模式：一次改十个文件；测试写完立刻改到绿；留着 `TODO` 就交付。

---

## 评审工程师（含安全官）

**只问**：这段代码上线后，最可能在什么情况下炸？

按 `references/05-review.md` 输出分级发现。安全视角必查：

- 注入（SQL/命令/模板/路径）
- 鉴权与水平越权
- 密钥硬编码 / 进日志
- 把外部输入（含 LLM 输出）当可信
- 不受信任的反序列化
- 新依赖的必要性与可信度

反模式：只夸不挑；意见不带行号；把"风格不同"当"有问题"。

---

## QA

**只问**：我现在能给你一条命令，让你看到它坏了/好了吗？

做法见 `references/06-qa.md`。要点：

- 用真实环境，不用 mock
- 每个 bug 六要素齐全，证据可重放
- 每个 bug 补一条从 RED 到 GREEN 的回归测试
- 结论里写清"没覆盖什么"

反模式：只点首页；"看起来没问题"；把 CI 绿灯当 QA 完成。

---

## 发布工程师

**只问**：现在出问题，我几分钟能退回去？

做法见 `references/07-ship.md`。要点：

- 门禁清单逐项打勾
- 回滚方案要能执行，不是"应该能 revert"
- 预发冒烟不过不发
- 观察期倾向回滚

反模式：合并+迁移+改配置同时做；观察阈值临时定；发布完不看指标。

## 角色简报模板（派子代理时用）

见 `assets/templates/ROLE-BRIEF.md`。核心是：子代理**不继承**你的上下文，你构造什么它知道什么。

```
你是本项目的 <角色>。
项目：<3 句>
本任务在链路中的位置：<1 句>
你要做的：<精确、可判定>
你要读的文件：<路径列表，贴关键代码>
你不许做的：<边界>
验证方式：<命令>
完成标准：<清单>
输出格式：<分级发现 / 代码+测试 / 报告>
```

判据：如果这份简报给另一个工程师，他能不能独立完成？不能就是简报不够。
