# 02 · 计划制定与三路审查（Plan）

> 计划的读者不是你自己，是**一个没见过这个代码库、没读过 spec 的人**。他能不能只靠这份计划写完代码，是计划好坏的唯一标准。

融合：superpowers 的 `writing-plans`（任务粒度）+ gstack 的四档范围模式与三路审查（CEO / 工程 / 设计）。

---

## 1. 计划不是任务清单

一份能用的计划，每个任务都包含这四项，缺一项就退回：

| 字段 | 内容 | 反例 |
|---|---|---|
| **文件** | 要新建/修改的具体路径 | "修改后端逻辑" |
| **接口** | 函数/端点/组件的签名、参数、返回、错误 | "实现解析功能" |
| **验证** | 证明它完成的那条命令或那个测试名 | "确保正常工作" |
| **完成定义** | 可观察的通过条件 | "功能可用" |

任务大小：**一个任务 = 一次提交 = 一次可独立验证**。经验值 30–120 行改动。超过 200 行，拆。

---

## 2. 先定文件结构，再定任务

任务分解的本质是**边界决策**，而边界体现在文件上。所以顺序是：文件 → 接口 → 任务。

决策原则：

- **一个文件一个职责。** 你能同时在脑子里装下的代码，才是你能可靠修改的代码。
- **一起变化的东西放一起**，按职责切，不按技术层切（不要 `models/` `handlers/` `utils/` 三件套）。
- **已有代码库遵循既有模式**，不要单方面重构。但如果计划要改的文件已经臃肿到装不下，把"拆分"作为计划里的一个显式任务。
- **接口先行**：先写签名和错误类型，再写实现。

产出这一段格式：

```
新增
  src/ingest/transcribe.ts      — 音频 → 文本，调用 ASR，失败抛 TranscriptError
  src/ingest/extract.ts         — 文本 → 行动项数组，纯函数，无 IO
  src/notify/feishu.ts          — 推送，重试 3 次，指数退避
修改
  src/jobs/nightly.ts           — 接入 ingest 流程，新增 1 个任务步骤
不动
  src/billing/**                — 本期完全不碰
```

"不动"这一栏要写。它防止范围蔓延。

## 3. 四档范围模式（CEO 视角）

在拆任务之前，先决定**做多少**。gstack 的 `/plan-ceo-review` 给四档，选一档并写进计划：

| 模式 | 含义 | 什么时候用 |
|---|---|---|
| **扩张 Expansion** | 找需求里藏着的 10 分产品，主动加范围 | 用户描述的东西明显小于他真正要的（说了"日报工具"，实际要"幕僚长"） |
| **选择性扩张** | 只加 1–2 个高杠杆项，其余砍 | 大多数情况 |
| **维持范围** | 严格照 spec 做 | 交付压力大、改动敏感 |
| **收缩 Reduction** | 砍到只剩验证核心假设的那一刀 | 需求没验证、预算紧、要在本周验证 |

选了就要在计划开头写出来：

```
范围模式：收缩
砍掉：多语言、历史归档、团队协作
保留：单文件上传 → 行动项 → 飞书推送
理由：还没有真实用户，先验证"抽出来的行动项有人看"
```

**默认推荐收缩。** 90% 的需求第一次做都不该做全。

## 4. 三路审查

计划写完后，用三个视角各过一遍。可以自己扮演，也可以派子代理。全部在 `PLAN.md` 里留痕。

### 4.1 工程审查（架构师 / 工程经理）

逐项回答，答不上就是计划有洞：

- **数据流**：从入口到落库，每一步的输入输出是什么？画 ASCII 图。
- **状态机**：有哪些状态？非法转移怎么处理？用表格列全。
- **错误路径**：每个外部依赖失败时发生什么？（超时、4xx、5xx、返回垃圾、返回空）
- **边界条件**：空输入、超大输入、并发、重复提交、时区、编码、精度。
- **隐藏假设**：计划里哪些地方是"应该没问题吧"？逐条列出来，能验证的先验证。
- **测试矩阵**：每个任务对应哪条测试？表格化。
- **安全**：鉴权、越权、注入、日志泄露、密钥存放。
- **迁移**：有没有数据结构变更？回滚怎么回？

```
数据流
  upload → [validate] → tmp/a.wav → [asr] → text → [extract] → items[] → [feishu] → ok
              ↓失败              ↓超时            ↓空               ↓429
          400 明确报错      重试2次后退回      返回空数组(不报错)   排队重试

状态
  pending → transcribing → extracting → notifying → done
    任何一步失败 → failed，可 retry；retry 3 次后 → dead（人工介入）
```

### 4.2 设计审查（资深设计师）

仅当有 UI 时做。对每个设计维度打 **0–10 分**，说明 10 分长什么样，然后**改计划**往那个方向靠：

| 维度 | 问题 | 及格线 |
|---|---|---|
| 视觉层级 | 用户 3 秒内看到的是最重要的东西吗？ | 7 |
| 布局与密度 | 留白是设计出来的还是漏出来的？ | 7 |
| 文案 | 每句话都在帮用户做决定吗？有空话吗？ | 7 |
| 空状态 / 加载 / 错误 | 三个状态都设计了吗？还是只有"正常"？ | 8 |
| 交互反馈 | 每个点击都有即时反馈吗？ | 7 |
| 一致性 | 间距、字号、圆角、色值来自同一套规则吗？ | 8 |
| AI 味检测 | 有没有紫蓝渐变、居中英雄区、三卡片并排、emoji 当图标？ | 无 |

**AI 味清单**（命中即扣分）：紫→蓝渐变背景、发光边框、居中对齐的大标题 + 副标题 + 双按钮、三列功能卡片配线性图标、玻璃拟态滥用、无意义的微交互动画、Inter 字体 + 灰底卡片 + 大圆角。

每个设计选择**一次只问用户一个**，带推荐项。

### 4.3 产品审查（CEO 视角）

- 这一版做完，**用户会说什么**？写出一句用户的原话预期。
- 如果只能留一个功能，留哪个？
- 有没有更便宜的验证方式（人工、脚本、现成工具）？
- 三个月后这件事还有意义吗？

## 5. 计划文档格式

模板：`assets/templates/PLAN.md`。必须包含：

```markdown
# 实施计划：<特性名>
日期 / spec 链接 / 范围模式 / 预计任务数

## 文件结构
（见第 2 节格式）

## 任务

### T1 · <动词开头的名字>
- 文件：src/ingest/extract.ts（新建）
- 接口：`extract(text: string): ActionItem[]`，空文本返回 `[]`，不抛异常
- 步骤：
  1. 写测试 `extract.spec.ts::空文本返回空数组` → 跑 → 必须 RED
  2. 最小实现 → 跑 → GREEN
  3. 写测试 `::含两个行动项` → RED → 实现 → GREEN
  4. 提交 `feat(ingest): 抽出行动项`
- 验证：`pnpm test src/ingest/extract.spec.ts`
- 完成定义：该文件全部测试通过，无 eslint 警告

### T2 · ...

## 风险
| 风险 | 概率 | 影响 | 对策 |

## 回滚
<怎么退回去>
```
