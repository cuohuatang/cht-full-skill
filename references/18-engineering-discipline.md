# 18 · 工程纪律：三段式工作法 + 量化质量门（受 ub-mode 启发）

> **灵感来源**：Robert C. Martin（"Uncle Bob"）的 [`ub-mode`](https://github.com/unclebob/ub-mode)（★★★★ 6.4k，2026-10 发布）。
> **合规说明**：ub-mode **未声明许可证（默认版权所有）**，本仓库**未复制其文件**，下表与命令均为**原创重述并署名**。其思想属 clean-code 通识，复述合法；其"三段式 + 量化门"被吸收进本 skill 的纪律层。
> **同伴工具**（crapper / dryer / mutator，均 0BSD）属语言特定的预编译度量二进制，**不在本仓库内分发**，仅作为可选外部门禁指针列出。

---

## 1. 为什么要有这一篇

`references/03-execution.md`（TDD）、`04-debugging.md`（根因）、`05-review.md`（评审）、`06-qa.md`（验证）已经覆盖了"怎么做才对"。

这一篇补的是 **三个他们没给的东西**：

1. **一段强制的做事顺序**——先交"能跑的最小改动"，再单独做"把它做对"的重构，不要混在一起。
2. **三个可量化的质量门**——复杂度、重复度、测试盲区，不再是"感觉好了"，而是有数字验收。
3. **一招根因排查法**——当多个修复都倒在同一个门上，先杀掉它们共享的那个前提。

---

## 2. 三段式工作法（原创重述）

> 每一次写代码或改代码，都走这三步，**顺序不可乱**：

```
① Make it Work  —— 先让它工作（最小可用）
        ↓
② Make it Right —— 再把它做对（按门禁重构）
        ↓
③ Practice       —— 收尾纪律（留痕 + 小步提交）
```

### ① Make it Work（先活下来）

| 纪律 | 做法 |
|---|---|
| 最小编辑 | 一个决策只落在一个地方；只发"解决问题的最小改动" |
| 先定形状 | 动手写逻辑前，先把数据的结构与流动定对 |
| **TDD** | 先写那条会失败的测试，看它按预期原因失败，再只做"让它过"的最小改动；写不出诚实测试就别写假测试 |
| 从第一性原理重做 | 不要往旧设计上硬挂新需求；问"如果一开始就设计，会建成什么样"，想透后分片交付 |
| **攻击前提** | 当两个共享同一前提的修复都倒在同一道门上：把前提用一句话写出来，数一数"谁持有了这个不平衡"，**移除这个赋值**，在没做完之前不开下一个修复 |
| 先减后加 | 在加任何东西之前，先把复杂度拿掉 |
| 做杠杆 | 工作一眼看不出头绪，就先造一个做它的工具——先手搓一个单元，再让工具对齐这个单元 |

### ② Make it Right（再做对）

| 纪律 | 做法 |
|---|---|
| 修根因 | 先复现，再修因；只把崩溃藏起来的 guard 不算修复 |
| 切成可验证单元 | 一个小单元做完就验证，再开下一个 |
| 测行为不测实现 | 测试得像它的用户那样调用，并查用户会看到的结果；"就算所有函数都返回空也照样过"的测试直接扔 |
| **过三道量化门**（见 §3） | CRAP < 10、重复度 < 0.8、变异测试 0 存活 |
| 重构纪律 | 先钉住"它现在做什么"，再改"结构"，最后证明行为没变 |

### ③ Practice（收尾）

| 纪律 | 做法 |
|---|---|
| 留痕 | 记录每一步动作与理由；**完成时把这本账报出来** |
| 守护上下文窗口 | 主线程保持小，正文外移，只留摘要 |
| 清理 | 找出能安全删除的东西，确认没人在用时再回收磁盘；未提交的改动先等人拍板 |
| 提交 | 小步、有序、频繁；每笔写清"为什么 / 改了什么 / 怎么证明"；最后推主线 |

## 3. 三道量化质量门（推荐基线）

> cht-full-skill 的门禁本以**行为**为准（见证失败测试、证明无回归）。ub-mode 把其中几条补成了**数字**，可直接拿来当硬门槛：

| 门 | 含义 | 推荐阈值 | 判读 | 工具（外部，0BSD） |
|---|---|---|---|---|
| **CRAP** | 圈复杂度 × （1 − 覆盖率），衡量"又复杂又没测"的方法 | **< 10** | ≥10 的函数必须拆分或补测（或两者都做） | [`unclebob/crapper`](https://github.com/unclebob/crapper)（Clojure/Java/Go/TS/Rust/Python） |
| **重复度** | 结构性代码重复相似度 | **< 0.8** | ≥0.8 的重复块必须消除 | [`unclebob/dryer`](https://github.com/unclebob/dryer) |
| **变异测试** | 注入随机改动，测试抓不到的"存活变异体" | **= 0** | 存活体 = 测试盲区；覆盖盲区、杀光存活体、删死码 | [`unclebob/mutator`](https://github.com/unclebob/mutator) |

**怎么用**：

- 这三道是**推荐基线**，不是强制红线——除非用户明确要求"过门禁才合并"，否则作为**重构到什么程度算够**的收尾标准。
- 工具支持的语言有限（见上）。**你的项目语言不在表里，就只用 §2 的行为纪律**，不要为了跑门禁而引入额外工具链（违背本仓库"0 运行时依赖"）。
- 绝不让"过了 CRAP/dup 数字"替代"做了真实环境 QA"——数字是**下限**，不是**等效**。

## 4. 与本仓库三条铁律的关系

| ub-mode 纪律 | cht 既有 | 关系 |
|---|---|---|
| Make it Work 的 TDD | 铁律②"没看见它失败的测试不叫测试" | **同一回事**，这里给了更具体的"先减后加 / 从第一性原理重做" |
| Make it Right 的修根因 | `references/04-debugging.md` 根因铁律 | 一致；ub-mode 补了"攻击前提"这一招 |
| 量化门 | `references/06-qa.md` 行为门禁 | **增量**：补了数字阈值 |
| Practice 留痕 + 小步提交 | `references/03-execution.md` ledger / `references/10-memory.md` | 互补；这里强调"完成即报账" |

**一句话**：铁律管"能不能进下一阶段"，本篇管"代码本身够不够干净、可不可量化验收"。

## 5. 反模式（本篇专属）

| 反模式 | 正确做法 |
|---|---|
| 把"做对"和"做出来"混在一遍里，写完一坨再修 | 先最小可用，再单独重构 |
| 多个修复都卡同一道门，却逐个打补丁 | 写下一句话前提，移除它 |
| "复杂度高就高呗，能跑就行" | CRAP < 10，拆或补测 |
| 测试只覆盖主路径，变异测试一片红 | 杀光存活变异体 |
| 改完不报账、不提交，留一堆未提交改动 | 小步有序提交 + 完成即汇报 |
| 为了跑量化门，给纯脚本项目硬塞重量级工具链 | 不在支持语言内就只用行为纪律 |
