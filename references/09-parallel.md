# 09 · 并行工作（Worktrees & Parallel Agents）

> 并行的前提是**互不干扰**。做不到隔离，就老老实实串行——并行产生的合并冲突，成本比节省的时间高。

---

## 1. 先判断是否该并行

```
有 2 个以上问题要处理？
├─ 否 → 串行
└─ 是 → 它们共享状态吗？（同一个文件、同一个测试套件、同一个数据库表）
        ├─ 是 → 串行（相关的问题一起查更快）
        └─ 否 → 能同时进行吗？
                ├─ 否（有先后依赖）→ 顺序派发
                └─ 是 → 并行派发
```

典型可并行：多个不同测试文件的失败、多个独立子系统的实现、多处独立的数据清洗、多个模块的文档补全。

典型不可并行：同一个函数的多处修改、需要共享一个开发服务器、需要按顺序执行的数据库迁移。

---

## 2. 工作区隔离：worktree

**第一步永远是检测是否已隔离**，不要重复创建：

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)

# 子模块保护：GIT_DIR != GIT_COMMON 在子模块里也成立
git rev-parse --show-superproject-working-tree 2>/dev/null   # 有输出 = 子模块，不是 worktree
```

- `GIT_DIR != GIT_COMMON` 且**不在子模块** → 已在 worktree，直接用。
- 否则创建：

```bash
git worktree add ../<repo>-<feature> -b feat/<feature>
cd ../<repo>-<feature>
```

清理（合并后）：

```bash
git worktree remove ../<repo>-<feature>
git branch -d feat/<feature>
```

原则：**先检测，再用平台原生能力，最后才手搓 git。不要跟工具链对着干。**

---

## 3. 并行代理分派

一个代理 = 一个问题域。不要给一个代理三个不相关的问题。

简报必须自包含（见 `references/08-roles.md` 末尾）：

```
你是 <角色>，处理 <问题域> 的 <具体问题>。
复现：<命令>
已知：<已经试过/排除的>
你要交付：<根因 + 修复 + 回归测试> 或 <只给根因分析>
边界：只改 <目录>，不许动 <文件>
验证：<命令>
```

派发后**不要中途接管**它负责的文件。你在主分支改同一个文件，等于制造冲突。

---

## 4. 合并纪律

合并前对每个分支：

```bash
git log --oneline main..feat/x        # 它到底改了什么
git diff --stat main...feat/x         # 规模
git merge-tree $(git merge-base main feat/x) main feat/x | grep -c '<<<<<<<'  # 预判冲突
```

规则：

1. **一条分支一个目的**。混了两件事就拆。
2. **合并前重跑测试**（分支上绿 ≠ 合并后绿，尤其涉及共享模块）。
3. **一次合一条**，合完跑一次全量，再合下一条。批量合并出问题时无法定位。
4. **用 `--no-ff` 保留分支痕迹**（除非仓库惯例是 squash）。
5. 冲突解决后必须重跑相关测试，不接受"只是解个冲突而已"。

---

## 5. 队长模式（多 lane 并发时的角色）

当你同时推进 3 条以上工作线：

```
Lane：一条独立工作线（一个分支 + 一个 worktree + 一个目标）
Captain：只做三件事——分派、验收、合并
```

Captain 的纪律：

- **不亲自写业务代码**。一写就丢全局视野。
- 每条 lane 完成时提交一个 `READY` 块：

```
READY lane/<name>
分支：feat/x ｜ 提交：a1b2c3d ｜ 测试：42 passed
改动：<3 条>
影响面：<会不会碰共享模块>
回滚：<怎么退>
```

- 合并按顺序排队（合并列车），一次一条，每次合并后跑全量。
- 每天固定一次"flaky 清理"：把不稳定测试单独修掉，不要带着它跑。

---

## 6. 常见翻车

| 现象 | 原因 | 处理 |
|---|---|---|
| 合并后测试大面积挂 | 分支上只跑了自己相关的测试 | 合并前跑全量 |
| 冲突反复出现 | 两条 lane 改了同一文件 | 重新切边界，或改串行 |
| 一个代理改了另一个代理的文件 | 简报边界没写清 | 简报里写死"只改 <目录>" |
| worktree 里的依赖跑不起来 | 各 worktree 需要独立安装依赖 | 每个 worktree 单独 install |
| 主分支被污染 | 直接在 main 上试 | 永远在分支/worktree 上做 |
