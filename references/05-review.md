# 05 · 代码评审（Review）

> 评审要回答的问题只有一个：**哪个问题能通过 CI，但在线上炸。**

不是"代码写得整不整齐"，不是"你喜不喜欢这种风格"，更不是"AI 写得快不快"。

---

## 1. 分级输出（每条发现必须归级）

| 级别 | 含义 | 动作 |
|---|---|---|
| `P0 阻断` | 数据错、安全漏洞、必崩、破坏兼容 | 不许合并 |
| `P1 严重` | 特定条件下出错、性能不可接受、无回滚 | 修完再合并 |
| `P2 一般` | 可维护性 / 边界遗漏 / 错误处理不到位 | 建议本期修 |
| `P3 提示` | 命名、注释、可读性 | 记录，不阻断 |
| `AUTO-FIXED` | 明显笔误、死代码、缺少 await 等机械问题 | 已直接修，列出改了什么 |
| `ASK` | 需要产品/架构决策的问题 | 停下来问，**不要自己拍** |

输出格式：

```
[P0] src/auth/session.ts:42 — 刷新 token 时未校验过期，重放攻击可获长期会话
     证据：<代码片段>  建议：<具体改法>
[AUTO-FIXED] src/ingest/extract.ts:18 — 缺少 await，已补
[ASK] src/jobs/nightly.ts:77 — 并发写入会不会冲突？取决于你的队列语义，需要你定
```

**禁止**：只输出"整体不错，建议优化性能"。没有文件行号的意见不是意见。

## 2. 重点审查项（按发现概率排序）

### 2.1 正确性

- 边界：空、1、多、超限、负数、零、极大
- 空值链路：`null`/`undefined`/`None`/空字符串 是否被区分对待
- 异步：每个 `await` 都在；并发下共享状态是否安全；错误是否被吞
- 错误处理：捕获了是否处理？还是静默？错误信息够不够定位？
- 资源：文件/连接/监听器/定时器是否释放
- 幂等：重复提交、重试会不会产生副作用

### 2.2 安全

- 注入：SQL、命令、模板、路径穿越
- 鉴权：每个新端点都校验了吗？水平越权（A 用户能读到 B 的数据）？
- 密钥：硬编码？进日志？进错误信息？
- 输入信任：来自外部的数据（含 LLM 输出）当成可信输入用了
- 反序列化：不受信任的 YAML/pickle/eval
- 依赖：新引入的包是否必要、是否可信、是否有已知漏洞

### 2.3 数据

- 迁移：是否可回滚？大表是否锁表？是否有默认值？
- 事务边界：多步写入是否在同一事务？部分失败会留下脏数据吗？
- 并发：用锁了吗？乐观锁版本号？丢失更新？
- 时区与精度：存 UTC？金额用整数分？

### 2.4 性能（只查会被真实触发的）

- N+1 查询
- 循环里发请求 / 循环里 await
- 无上限的分页 / 全表扫描 / 无索引查询
- 大对象拷贝、同步阻塞 IO 在主线程

### 2.5 门禁完整性（重点，最容易被悄悄破坏）

逐个检查 diff 里有没有这些**降级**动作：

| 降级动作 | 危害 | 处理 |
|---|---|---|
| 断言被改宽 / 删除 | 测试变恒真 | P0，必须还原并说明 |
| 新增 `.skip` / `@Ignore` / `xfail` | 测试静默失效 | P0 |
| 超时时间被调大 | 掩盖性能退化 | P1，要求给出原因 |
| 快照被无脑更新 | 变更不再被审查 | P1 |
| 异常被 `try/catch` 吞掉 | 失败不可见 | P1 |
| lint 规则被禁用 / `any` 泛滥 | 类型安全失效 | P2 |
| 覆盖率阈值被下调 | 门禁失效 | P0 |

**每一个降级都要点名到人**：谁改的、为什么、什么时候恢复。写进 `REVIEW.md`。这类改动是"让门禁看起来还在"的最常见方式。

## 3. 评审流程

```bash
BASE=$(git merge-base origin/main HEAD)
git diff --stat $BASE..HEAD        # 先看规模，超过 400 行要拆分评审
git diff $BASE..HEAD               # 逐个文件读，不要跳
```

顺序建议：先读 diff 的**结构**（改了哪些文件、新增了什么依赖）→ 再读**核心逻辑** → 最后读**测试**（测试能告诉你作者以为自己在做什么）。

评审要独立于作者的自述。"我在描述里写了它做什么"不是证据，diff 是证据。

## 4. 接收评审的纪律（给自己用）

收到评审意见时，禁止两种表演：

- **无条件同意**："你说得完全对！" —— 这不是技术判断。
- **无条件辩护**："这是有意为之。" —— 除非你能指出代码里的证据。

流程：

```
1. 读完，不反应
2. 用自己的话重述要求（不确定就问）
3. 对着代码验证：这个意见在这份代码库里成立吗？
4. 评估：技术上是更好了，还是只是不同？
5. 回应：技术性确认，或有理有据的反驳
6. 实施：一次一条，每条都跑测试
```

反驳的正确姿势：

```
我理解你的担心是 <X>。在 <具体位置> 用的是 <机制>，所以 <X> 不会发生。
如果你说的是 <另一种情况>，那确实有问题，我会 <改法>。
```

**禁止的回应**：`You're absolutely right`、`好建议，已全部采纳`、沉默地全改。

## 5. 自审清单（提交 PR 前自己过一遍）

- [ ] diff 里没有调试代码、注释掉的旧实现、无关格式化
- [ ] 每条新增逻辑都有对应测试，且测试能失败（试过）
- [ ] 没有降级门禁的动作，或已明确记录原因与恢复时间
- [ ] 错误信息对"下一个看日志的人"有用（含上下文，不含密钥）
- [ ] 公开接口变更已在 CHANGELOG / API 文档体现
- [ ] 依赖新增有理由，且锁文件已提交
- [ ] 回滚方式明确（revert 这个提交够吗？需要数据回滚吗？）
