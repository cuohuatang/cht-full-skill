# 提示词架构师 · 阶段 -1 前置闸门

> 用户不会写提示词，只要说出**使用场景和用途**；本关负责把它变成可直接交给任意 Agent 的提示词。
> 但**不是所有输入都优化**。这一条比"怎么优化"更重要，所以先讲闸门，再讲优化。

方法论来源：本仓库用户提供的原创提示词，经 cht 结构化整理、边界划死与可执行化。**不是第三方开源项目**，不引入新许可，见 `NOTICE.md`「本仓库新增的部分」。

---

## 1. 裁决主轴：规格完整度

不要靠"这句话像不像任务"去猜。只问一件事：

> **这段输入本身，是否已经构成一份完整可执行规格？**

| 判断 | 含义 | 动作 |
|---|---|---|
| 是 | 角色、范围、格式、验收都已确定，或根本不需要这些 | **原样透传**，一个字不改 |
| 否 | 缺角色设定 / 隐性需求 / 风格约束 / 输出格式 / 边界 | **优化**，出双版本 |
| 拿不准 | 既不像任务也不像禁止项 | **默认透传**，不擅自改写 |

这条主轴能统一解释所有禁止项，比逐条死记可靠：寒暄没有任务、事实问答答案确定、翻译/摘要输入即规格、延续性修改的上下文已完整、点名技能或文件已给出精确执行路径——**它们都不缺东西，优化只会往里塞无效指令**。

**灰区默认透传**是刻意设计：漏优化的代价是用户多说一句，过度优化的代价是 AI 擅自改写意图。后者贵得多，且与 `grill-me` 决策护栏同源。

---

## 2. 硬闸门：禁止优化清单

优先级从高到低，**先命中先裁决**。可执行实现见 `scripts/prompt_gate.sh`。

| 规则 | 禁止优化的输入 | 为什么 |
|---|---|---|
| **R0 一票否决** | "不要优化 / 原样 / 直接回答 / 只判断别改"、"对不对？""是不是？"这类只要判断的请求 | 用户已明确表达意志，任何优化都是违令 |
| **R1 寒暄致谢** | 你好 / 谢谢 / 收到 / 辛苦了 / 好的 | 无任务可优化；回一段"我判断不需要优化"本身就是废话 |
| **R2 纯事实问答 / 翻译 / 摘要** | "什么是 TCP 三次握手""把这段翻译成英文""把这段缩成 100 字" | 单步、无歧义、输入即完整规格 |
| **R3 延续性修改** | "继续""换成蓝色""把标题改成 24px""撤销 / 重试" | 依赖既有上下文，优化会破坏连续性 |
| **R4 已点名技能或文件** | `/cht-audit 审一下`、`@SKILL.md`、`打开 references/07-ship.md` | 执行路径已精确，优化是无效指令 |
| **R9 灰区** | "嗯""看看""关于上周那个" | 默认透传 |

### 关键灰区：摘要 ≠ 归纳总结

用户把「摘要」列进禁止项、把「归纳总结」列进任务型，区别不在词面，在**有没有多出来的交付要求**：

| 输入 | 裁决 | 依据 |
|---|---|---|
| 把这段缩成 100 字 | 透传 | 输入即规格，一步做完 |
| 把这段话翻译成英文 | 透传 | 同上 |
| 归纳总结这个项目的问题并给出改进方案 | **优化** | 多来源 + 分析 + 结论 + 方案，缺角色与格式 |
| 把这份技术文档本地化并输出术语表 | **优化** | 有交付物、有验收边界 |
| 把 CSV 转换成 JSON 并产出文件 | **优化** | 「转换」是任务，不是「改成」式延续 |

一句话：**单步转换不优化，带分析 / 结论 / 方案 / 交付物 / 多来源就优化。**

### 其他边界

- **寒暄夹带新任务**：「谢谢，帮我生成一份报告」→ **优化**（寒暄不是豁免牌，R1 只在后面没有任务动词时生效）。
- **延续夹带新任务**：「继续，顺便把订单模块重构一遍」→ **优化**，因为出现了新任务动词。
- **"转换成"不是"换成"**：中文子串会骗人。`scripts/prompt_gate.sh` 已用「有任务动词则跳过 R3」挡掉，自测里有专门样例。

### 硬闸门怎么用

```bash
scripts/prompt_gate.sh "帮我安装并配置好 PostgreSQL"   # → OPTIMIZE
scripts/prompt_gate.sh --why "换成蓝色"                # → PASS_THROUGH  R3 延续性修改…
scripts/prompt_gate.sh --selftest                     # 26 例，全过才算可用
```

脚本是 **POSIX sh、0 依赖、`LC_ALL=C`**，只做确定性预检，输出 `PASS_THROUGH` / `OPTIMIZE` / `AMBIGUOUS`。它给不出语义理解，**最终裁决仍由宿主结合上下文做出**；脚本判 `AMBIGUOUS` 时按透传处理。不要把它当成万能分类器，也不要绕过它凭感觉决定。

## 3. 任务型清单（这些才优化）

下任务、归纳总结、生成、安装、修复、转换、推送、产出文件、重构、部署、检测、审计、造技能……**一切"重要任务"**。

共同特征：用户说了**场景和用途**，但没说清谁来干、按什么标准、交什么格式、什么算做完。

---

## 4. 四步优化规范

只有闸门判 `OPTIMIZE` 才执行，四步全做，不增不减。

### ① 补齐没说出口的隐性需求

自动补上**角色设定、风格约束、输出格式**，以及必要的边界与验收标准。

> **⚠️ 只补表达层，绝不补业务层。** 可以给"你是资深 DBA，输出 Markdown 表格，先结论后依据"，**不许**擅自加"顺便把备份也做了""再加个图表"。补需求 creep 就是擅自做主，直接违反 `grill-me` 护栏与 `references/01-discovery.md` 的范围纪律。

用户原话里的**数字、路径、文件名、报错串、专有名词逐字保留**，一个字符都不能改写。

### ② 出两个版本

| 版本 | 定位 | 内容 |
|---|---|---|
| **精简通用版** | 复制进任何聊天框就能用 | 角色一句 + 任务一句 + 输出格式一句 + 关键约束 2~3 条。**不写宿主专属语法** |
| **高阶顶配版** | 给有文件/shell/子 Agent 的 Agent | 在通用版之上补：上下文与输入材料、分步骤、验收标准、边界与非目标、失败降级、反例、自检清单 |

两版都是**完整可独立使用**的提示词，不是"大纲 + 补充说明"。用户没指定时两版都给；`--lite` / `--full` 可只取一版。

### ③ 结构化排版

固定用标题 / 列表 / 表格 / 代码块，**不寒暄、不复述需求、不闲聊、不凑字数、不写"希望对你有帮助"**。优化结果里唯一该出现的内容，就是可以直接复制走的提示词本身。

透传时更极端：**原样输出用户输入，连"此输入无需优化"都不写**——用户要的是执行，不是听汇报。

### ④ 自动适配所有 Agent，规避逻辑漏洞与无效指令

见第 5、6 节。

## 5. 全 Agent 适配矩阵

用户点名的 ChatGPT、Claude Code、豆包、DeepSeek、harness、Kimi 等，差异主要在**有没有文件系统 / shell / 子 Agent / skill / 长上下文**。精简通用版必须对所有宿主都成立。

| 宿主形态 | 代表 | 写提示词时 |
|---|---|---|
| 纯网页聊天，无文件无 shell | ChatGPT 网页、豆包、DeepSeek 网页、Kimi 网页 | 用自然语言描述，**不写路径、命令、skill 名、@引用**；要产出物就明确"以 Markdown 代码块给出全文" |
| 本地编码 Agent，有文件 / shell / 子 Agent / skill | Claude Code、CodeBuddy、Cursor、各类 harness | 可写路径、验证命令、文件产出、门禁；但**每条能力都要带降级**："若当前环境不支持 X，则改为 Y" |
| 长上下文 / 多材料 | Kimi、支持长文档的宿主 | 可塞多来源，但必须写死"只依据以下材料，材料外的内容标注为推断" |
| API / 无状态 harness | 一次性调用、无会话记忆 | 提示词必须**自包含**，禁止出现"上文""刚才那个""按之前的"等依赖会话的指代 |
| 本仓库 `cht-full-skill` | 当前宿主 | 可直接用 `/cht-*` 命令；但**高阶顶配版里要注明哪些是 cht 专属**，通用版里一律改写成自然语言 |

**适配的不是措辞，是能力边界。** 给一个没有 shell 的网页版塞"运行 `npm test` 并贴出输出"，就是典型的无效指令。

## 6. 规避逻辑漏洞与无效指令（逐条自检）

优化完，逐条过一遍；任何一条不过就重写：

1. **无软约束**：删掉"尽量 / 尽可能 / 适当 / 合理地 / 看着办"——无法判定做到没做到。每条约束都要能用"做到 / 没做到"二分。
2. **无自相矛盾**：「尽量简短」和「详细展开每一项」不能同时出现；要分优先级或分节。
3. **无宿主越权**：不要求无 shell 的宿主执行命令、不要求纯聊天窗口读写本地文件；能力必须带降级路径。
4. **无否定堆叠**：不写"不要不…""除非不…"，改成正向陈述。
5. **无会话依赖**：不出现"上文 / 刚才 / 按之前的 / 同上"，除非明确标注这是延续性任务（而延续性任务本就不该被优化）。
6. **无宿主专属黑话外泄**：通用版里不出现 `/cht-xxx`、`@file`、`SKILL.md` 等只在特定 Agent 有效的语法。
7. **无空洞角色扮演**：「你是世界顶级专家」这类不可验收的形容词，要么换成具体经验约束（"按 DBA 的回滚优先原则"），要么删掉。
8. **事实逐字保留**：数字、路径、错误串、专有名词、否定词（"不要 / 禁止 / 除外"）一个都不能丢或改。
9. **不越权扩范围**：不新增用户没提的功能、文件、交付物。
10. **可验收**：结尾至少有一条"什么算做完"的判据。

## 7. 与 cht 既有机制的边界（必读，别打架）

| 机制 | 干什么 | 与本关的关系 |
|---|---|---|
| **本关（阶段 -1）** | 把用户输入**翻译成可执行提示词** | 在一切之前，只碰表达层 |
| 阶段 0 `/cht-spec --discover` 六问 | **逼问真实需求** | 在本关**之后**。本关不追问、不代替逼问——优化提示词 ≠ 澄清需求 |
| `grill-me` 决策护栏 | 动手前盘问、防擅自做主 | 本关受它约束：不擅自补业务功能、灰区默认不动 |
| `caveman` 输出压缩 | 压缩**会话输出** | 一个管输入、一个管输出；两者都不碰验证证据与 `docs/cht/` 产出物 |
| 三条铁律 | 没证据不许说完成 | **铁律优先**：优化后的提示词不得要求"跳过验证 / 不用跑命令 / 说完成即可" |
| 13 道门禁 / `/cht-ship` | 发布门禁 | 本关不替代任何门禁，也不构成"已完成"的证据 |

**冲突时永远是：三条铁律 > 用户明确意志 > 本关规则 > 精简/顶配偏好。**

---

## 8. 红牌（出现即判本次优化作废）

- 改写 `PASS_THROUGH` 类输入，或在透传时附加解释、寒暄、"已判断无需优化"之类旁白
- 用户说「只判断」时仍塞出两个版本
- 借「补齐隐性需求」新增业务功能、扩大范围、替用户做决定
- 丢掉或改写原话里的数字、路径、报错串、否定词
- 把通用版写成 cht 专属命令，或给无 shell 宿主塞 shell 命令
- 优化结果里出现寒暄、复述、凑字数、"希望有帮助"
- 对同一段输入既报「不优化」又给两版
- 拿优化结果冒充验证证据（提示词写得再好也不等于任务做完了）
